"@emdash-cms/cloudflare": minor

The Cloudflare Email Sending provider now checks every message before it reaches the binding. A `to` or `cc` that is not one plain address is refused, and a `replyTo` that is not is dropped, so form input cannot add a recipient or start a header. A `cc` is refused unless the config allows it (`allowCc`): a binding restricted to some recipients is only known to check `to`. The subject and the sender's name lose their control characters (CR and LF among them). Recipients are counted in the site's database, each count one compare-and-set row (`limits`): each sending source (auth mail, the admin's test email, each plugin) 50 an hour and 200 a day, every source together 300 a day, of which 50 are kept for auth mail (`systemReserve`) so forms and comments cannot spend the day the login email needs, and auth mail 10 a day to any one address, so requests from rotating IPs can neither flood one inbox nor spend the day. A message the binding refuses gives its places back. A send moves only its own counts and deletes none; the counts of windows that are over go in a daily cron task, at most 500 a run, and never the current window's or the one before it. With `broker`, the provider sends nothing from the site's Worker: after these checks and the site's own budget, every message goes to the site's mail broker (`@emdash-cms/cloudflare/auth-mail/worker`, a Worker of its own reached through the service binding `MAIL_BROKER`) as a fixed envelope with the site's generation capability (`MAIL_BROKER_CAPABILITY`) and a request id, in the broker's protocol (`MAIL_BROKER_PROTOCOL`, 2); the broker alone holds the send_email bindings and the account's mail-budget tokens. A missing binding or capability, or a refusal, sends nothing and gives the site's places back; a call that throws is asked once more with the same request id (the broker never sends one request id twice), and a call with no answer that says sent or refused (none within `broker.timeoutMs`, 5 s, among them) is reported as not known to be sent and keeps the site's places. `CLOUDFLARE_EMAIL_CAPABILITY` names what the provider enforces (`...,mail-broker;v=3`); the status route answers it, so a built Worker carries it and a deployment can check a build for it before turning its email on. The status route's `attestation` (version `EMAIL_ATTESTATION_VERSION`, 3) says in machine-readable form what the build guarantees (headers checked, the site's budget, every message through the broker, a cancelled send reported as cancelled, addresses redacted) and, with `broker`, the broker protocol it speaks, the generation the Worker was given (`MAIL_GENERATION`), the SHA-256 of its capability, and the broker's live, read-only status for that capability: whether it is the broker's active or staged generation's, the site and deployment the broker is configured as, the capability's and the budget tokens' hashes, and the account's budget's report of each lane. It never carries the capability, a token or a recipient, and sends, takes and refunds nothing. Logs name a recipient's domain, never the address, and an error the binding throws has the address replaced by its domain. Without `from.name`, the sender's name is the site's title. A new "Reply-To address" setting holds the site's own address for messages that name no reply-to, and a `status` route says the sender, whether the Worker has the binding, and where replies go.
