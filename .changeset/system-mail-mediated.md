Adds the `systemMail: { binding, capability }` option. With it, the magic-link, sign-up, invite and admin recovery routes send EmDash's own sign-in mail through the site's mail broker: a separate Worker bound to the site as a service (`@emdash-cms/cloudflare/auth-mail`). Every request carries the site's generation capability (the secret `capability` names, `MAIL_BROKER_CAPABILITY` by default), which the broker checks first; it then authenticates the request, issues the token, renders the message and sends it itself. These routes then never build or send that mail in the site's Worker, so no plugin hook can see it. If the binding or the capability is missing, nothing is sent and the routes never fall back to the site's own email pipeline; an invite still returns its copy link. Each operation names a request id, and a call whose answer is lost is asked once more with the same id, which the broker answers as it answered the first, so one operation is never run twice. When whether the mail went is not known (the broker says `unknown`, the call is lost twice, or the answer is not the broker's), an invite makes no second invite and answers `502 INVITE_EMAIL_UNKNOWN`, and a recovery link answers `502 RECOVERY_SEND_UNKNOWN`; neither says the mail was not sent. `GET /_emdash/api/settings/email` reports `systemMail`, including the broker's own status for the site's capability.
