A site's mail now goes out through one door: its mail broker (`@emdash-cms/cloudflare/auth-mail/worker`). The broker's Durable Object holds the site's generations: the operator stages a generation (the SHA-256 of the capability it gives the site's Worker, and the generation's two mail-budget tokens) and activates it, through the broker's admin door (`/admin/stage`, `/admin/activate`, `/admin/retire`, `/admin/state`, behind `BROKER_ADMIN_SECRET`, which the entrypoint checks before a request reaches the object, so a request without it never wakes the object). Only the active generation's capability counts: a staged, retired or unknown one is refused before anything is read, written, counted or sent. Every call (each send, each sign-in operation, each status, and every admin call) takes its turn in one queue and runs to its end before the next starts, the `send_email` call and the give-back of a refused one included, so an activation or a retire answers only after every call before it has ended, and no call with the old capability sends after that answer. A give-back is owed in the object's storage before the mail budget is asked for it, and kept until the budget answers it: an activation is not made, and a retire is made but not acknowledged (503, with `owedRefunds`), until every give-back an earlier send owes is settled, across a restart too. A take whose answer never came is given back by the request id it was asked with. The active generation is in the object's storage, so an eviction, a restart or an upload of the broker keeps it. `send({ protocol, capability, requestId, message })` takes exactly `{ to, cc?, subject, text, html?, replyTo? }`: the sender and every other header are the broker's; each recipient must be on the broker's list (`BROKER_RECIPIENTS`); a request id the same capability used before answers what it came to and sends nothing again, whichever generation is active by then (only new work is held to the active generation, so a retry of a send whose answer was lost across an activation is never told `refused`), a request id another capability used answers nothing, and one whose first attempt never finished (the object stopped inside the send) answers `unknown`, never `refused`, since that message may have gone; the site's email provider then keeps the site's own places and reports it as not known to be sent. Among the calls waiting, the operator's go first, then the site's, then anonymous sign-in requests (magic links, sign-ups), of which at most 16 wait (one more runs nothing: a retry of one of them is told what it came to, or `unknown` while it is still waiting, and any other is refused at once), so a flood of sign-in requests cannot hold an activation or a retire; a running call is never cut short. Each call's answer carries its place in the order the queue ran calls in (`seq`). A take the budget answers as given back already is never a place to send in. Every sign-in operation names a request id too (broker protocol 3, marker `emdash-auth-mail:broker;v=3`): the broker remembers `unknown` just before EMAIL_SYSTEM is asked to send and then what the operation came to, so a retry of one that stopped inside that send answers `unknown`, mints no second token and sends nothing again. The mail budget's protocol is 3: a take names a request id, and answers its generation.
