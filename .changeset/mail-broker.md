A site's mail now goes out through one door: its mail broker (`@emdash-cms/cloudflare/auth-mail/worker`). The broker's Durable Object holds the site's generations: the operator stages a generation (the SHA-256 of the capability it gives the site's Worker, and the generation's two mail-budget tokens) and activates it, through the broker's admin door (`/admin/stage`, `/admin/activate`, `/admin/retire`, `/admin/state`, behind `BROKER_ADMIN_SECRET`, which the entrypoint checks before a request reaches the object, so a request without it never wakes the object). Only the active generation's capability counts: a staged, retired or unknown one is refused before anything is read, written, counted or sent. Every call (each send, each sign-in operation, each status, and every admin call) takes its turn in one queue and runs to its end before the next starts, the `send_email` call and the refund of a refused one included, so an activation or a retire answers only after every call before it has ended, and no call with the old capability sends after that answer. The active generation is in the object's storage, so an eviction, a restart or an upload of the broker keeps it. `send({ protocol, capability, requestId, message })` takes exactly `{ to, cc?, subject, text, html?, replyTo? }`: the sender and every other header are the broker's; each recipient must be on the broker's list (`BROKER_RECIPIENTS`); a request id seen before answers what it came to and sends nothing again, and one whose first attempt never finished (the object stopped inside the send) answers `unknown`, never `refused`, since that message may have gone; the site's email provider then keeps the site's own places and reports it as not known to be sent. Each call's answer carries its place in the queue (`seq`). The mail budget's protocol is 3: a take names a request id, and answers its generation.
